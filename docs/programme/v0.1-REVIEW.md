# v0.1 Review — independent audit, effectiveness tests and target architecture

> Part of the **v0.2 working set** with [`BRIEF.md`](BRIEF.md) (intent; see its §21 capability-tier addendum) and [`PAID-TOOLS.md`](PAID-TOOLS.md) (how the commercial detectors work and what accuracy is realistic). This document owns the audit evidence, the target architecture (§8) and the phased v0.2 plan (§7).

Date: 27 August 2026 (updated same day with the full six-check test, the paid-tools findings and the v0.2 brain specification)
Author: Claude (independent audit for the owner; no publication action taken)
Scope: first-hand code audit of `implementation/`, empirical tests of all six advertised checker functions against the built engine, comparison with the snapshotted open-source tools, brief-wording analysis, and a target architecture plus revised plan. This review did **not** rely on the programme's own traceability matrix; every claim was verified against source code or produced by running code. Test scripts live in the session scratchpad (`head2head.mjs`, `patterns-test.mjs`, `checks456.mjs`) and run with Node 20+ against `implementation/packages/core/dist`.

## 1. Summary

The v0.1 build is a well-engineered delivery system around an intentionally thin, entirely from-scratch analysis engine. Of the six checks the live checker page advertises, three run real analysis (two of those on very small data tables), one records data without enforcing anything, and two are permanent stubs that cannot produce a result for any input in this release. The engine is correct within its declared scope, has no false positives on human text, and is outperformed by the free MIT-licensed tools in this programme's own `source-snapshots/` folder on invisible-character coverage, homoglyph coverage and writing-pattern detection. The brief never actually mandated reuse, which is how this happened without breaching a written rule. The fix is cheaper than it looks because the architecture already has the seams, and §8 sets out the "one brain, many shells" architecture to make every surface consistent and competitive.

## 2. Does BRIEF.md make the reuse intention clear?

**No.** The owner's intention — build upon existing open-source work rather than start from scratch — is not stated as a requirement anywhere in `BRIEF.md`.

- `BRIEF.md` §4 requires recording, per component, "whether Opace reuses, adapts, references or **excludes** it". Exclusion is an equally valid outcome; the only hard rule is negative ("No unlicensed, misleading or legally unclear code").
- §6.6 "Shared Open-Source Core" means Opace publishes its own code as open source — not that it builds on others'.
- The intention only appears in `research/OPEN-SOURCE-LANDSCAPE.md` ("Use the official C2PA JS packages… Adapt the deterministic writing-pattern rules from `avoid-ai-writing`…"), which is a research note, not a binding spec.
- `specs/04` then opened the door: "Prefer adapter processes **or clean-room implementation** from papers/specifications where licence or dependency weight makes direct reuse unsuitable." The build took the widest reading and clean-roomed everything.

**Recommendation:** add one binding rule to `BRIEF.md` §4: *"Where a researched component is permissively licensed, maintained and materially more capable than an Opace-written equivalent, the default is to adapt or wrap it with attribution. Building from scratch requires a recorded reason (licence, security, size or quality), per component."*

## 3. Empirical test of all six advertised checks

The live checker page offers six checkboxes. I traced each to its implementation in `integrity-controller.ts` and the core, then tested every one that can execute. Same engine ships in the website checker, WordPress 1.0.4, Chrome 1.0.0, Astro 0.1.0 and the CLI, so these results apply to every surface.

| UI check | What it actually is | Test result |
|---|---|---|
| 1. Invisible Unicode | Real: 7 named characters + 9 bidi controls ([unicode/inspect.ts](implementation/packages/core/src/unicode/inspect.ts)) | **6/6 covered carriers found; 0/9 classic watermark carriers found** (ZWNJ, ZWJ, NNBSP, hair space, tag characters, VS16, CGJ, MVS all pass silently) |
| 2. Homoglyphs | Real: same function, a 7-character Cyrillic confusable map | **Caught U+0430 (а) and U+043E (о); missed Cyrillic і (U+0456), Cyrillic к (U+043A) and Greek ο (U+03BF)**. The snapshotted `avoid-ai-writing` maps 24 Cyrillic + 6 Greek confusables |
| 3. Writing-pattern hints | Real: 5 stock phrases + repeated-opening rule + transition-density ratio ([patterns/en-gb-v1.ts](implementation/packages/core/src/patterns/en-gb-v1.ts)) | **7 findings on 2023-era clichés (works); 0 findings and a green `pass` on current-generation AI text** that upstream scores 47/100 with 9 issues; 0 false positives on human control text |
| 4. Protected facts and links | Partial: spans are extracted and displayed, but the UI row hardcodes `not_run` — "no comparison gate ran". Nothing is enforced in the checker | Extractor found currency, numbers, dates, URL, email, quote, code, time, unit correctly — but **no person names, no company names and no citation** ("Dr Sarah Chen", "Opace Ltd" and "(Chen et al., 2025)" were not extracted). Names and citations are the first items in `BRIEF.md` §7's Protect list |
| 5. Supported provenance | **Stub.** No C2PA reader exists anywhere in the codebase; the UI hardcodes "Text input has no supported provenance asset to inspect", and the only accepted uploads are `.txt`/`.md`/`.html`, which can never carry supported provenance | Confirmed: `provenance.c2pa` returns `unsupported` for every input. This checkbox cannot produce a result in v0.1 |
| 6. Named local signals | **Stub.** No detector exists; the UI hardcodes `not_configured` ("No additional local detector was configured") and there is nothing a user could configure | Confirmed: `detector.binoculars` (and any detector ID) returns `unsupported`. This checkbox cannot produce a result in v0.1 |

Fixture detail for checks 1–3 (five fixtures, run head-to-head with the snapshotted MIT `avoid-ai-writing` detector):

| Fixture | Opace core | Upstream `avoid-ai-writing` |
|---|---|---|
| A — carriers Opace names (ZWSP, BOM, SHY, NBSP, thin space, WJ) | 6/6 found | 1 issue (bypass-char flag) |
| B — carriers Opace omits (ZWNJ, ZWJ, NNBSP, hair, tag ×2, VS16, CGJ, MVS) | 0/9 — clean report | flags ZWNJ/ZWJ |
| C — classic AI clichés ("delve into", "in conclusion", repeated openings) | 7 findings | 10 issues, score 32 |
| D — current AI slop ("Great question!", "isn't just X — it's Y", "stands as a testament", "As of my last update") | 0 findings, status `pass` | 9 issues, score 47 |
| E — human control (mundane office memo) | 0 findings (correct) | score 0 (correct) |

**Owner confirmation on the live build:** the owner pasted the same 2,913-word GPT-5.6 article (scored 100% AI by both Copyleaks and Originality — see `PAID-TOOLS.md`) into the running checker page: result "0 finding groups need review · 2 checks passed · 4 checks were not run or unavailable". This reproduces, on the real UI, exactly what the fixture tests predicted: the current tool is not comparable to the paid detectors on AI detection, in either brain or presentation.

### Why "modern AI slop" returned zero — isn't it the easiest to detect?

Yes, it is the easiest to detect — *if the rules exist*. Detection of this class is pure pattern-matching over a large, current library: cliché lists, cutoff disclaimers ("As of my last update…"), formulaic openers ("Great question!"), "isn't just X — it's Y" constructions, em-dash density, rule-of-three, plus cheap stylometrics (sentence-rhythm burstiness, vocabulary diversity, function-word repetition). None of that is hard engineering; it is accumulated rule data. Opace shipped exactly five phrases, all from the 2023 cliché era, and none of the modern markers. Fixture D contains eight distinct signals the upstream free tool catches; Opace's list contains zero of them, so the engine correctly reported that its five phrases were absent — and then presented that as a green `pass`. The failure is not the engine's logic; it is that the rule library was rewritten small instead of adapted whole. This is simultaneously the worst gap and the cheapest fix in the entire product.

### What the tests prove overall

1. The engine is precise and honest within scope, with clean spans, hashes, limitation text, and zero false positives on human writing. The plumbing deserves to be kept.
2. The advertised surface overstates the product: six checks are offered, three-and-a-half exist. Fixture B — precisely the payload the viral `watermarks-remover` project scans for — produces a clean report.
3. The `pass` status communicates more assurance than a 5-phrase rule set can support. Scope it ("no findings from 8 rules") or cap it at `inconclusive` until the rule library is credible.
4. Protected-span extraction misses the brief's two headline categories (names, citations); everything regex-shaped works well.

## 4. Other first-hand audit findings

- **Zero integration of researched open source.** Confirmed from `THIRD_PARTY_NOTICES.md` and every manifest: runtime dependencies are utility libraries only (ajv, canonicalize, entities, jsonschema, rfc8785, opis/*). No copied code either — licence hygiene is genuinely good.
- **The analysis core is ~39KB of TypeScript**; the WordPress analyser is an 8.5KB PHP parity file; every other surface bundles the same Worker. Around this sit ~990 test files, tri-language contracts, SBOMs and full a11y evidence — the pipeline is an order of magnitude more engineered than the engine it delivers.
- **The integration seams exist and are unused**: `registerPatternPack()` in the core, `detector.*`/`provenance.c2pa` capability IDs in Spec 04, and a finished Python loopback job engine with no heavyweight jobs to run.

## 5. Was "from scratch, influenced by research" the right approach?

**Split verdict — right for the skeleton, wrong for the brain.**

Right and worth keeping: contracts, receipts, statuses, span/diff/gate mechanics, the seven delivery surfaces, the MIT-core/GPL-WordPress licence boundary, the loopback engine's security model. Nothing existed to reuse there, and clean ownership pays off.

Wrong and costing real capability: the Unicode carrier table and homoglyph map are *data*, not invention — rewriting them smaller produced a checker that fails its headline use case. The writing-pattern library is accumulated editorial knowledge — a clean-room 5-phrase substitute is the "basic cleaner" the brief promised to surpass. Provenance (`c2pa-js` is the official implementation) and detection (models and maths, impossible to clean-room) simply don't exist in the product; "influence only" there means "absent".

The multi-surface requirement sharpens this: seven shells multiply whatever the one core can do. Multiplying a thin core produced seven thin tools; upgrading the core once upgrades all seven.

## 6. Most useful test you can run now (pre-publication)

The standing **adversarial fixture battery**, three-fifths of which this review has now executed:

1. **Carrier battery** — every invisible/format character from the full Unicode `Cf`/`Zs`/tag/VS inventory embedded in clean text, through the real checker UI. Current score: 6 caught, 9+ missed. Target: 100%.
2. **Homoglyph battery** — the full confusables inventory. Current: 2 of 5 sampled.
3. **Live-model slop battery** — 20–30 passages from current Claude/GPT/Gemini across content types plus 20 verified-human passages (pre-AI Opace client copy). Score findings on AI text, false positives on human text, and `pass`-where-upstream-flags events. Current sample: Opace `pass` on text upstream scores 47/100.
4. **Cleaned-text battery** — AI text run through the viral remover first, then through Opace: what still fires?
5. **Protected-span fidelity battery** — dense fact text; verify extraction (now known to miss names/citations) and that safe-fixes never touch a protected span.

All local, no accounts, no publication. Wire the battery into `implementation/tests/` as golden fixtures — it then becomes the release gate for every capability below and the evidence base for any public "better than X" claim.

## 7. The v0.2 plan

Principle: keep the Opace skeleton; fill the brain through the existing seams. Do not publish any surface while fixture B or fixture D produces a clean report — v0.1 as published would be demonstrably outperformed by the free tools it researched, which is the reputational outcome `BRIEF.md` most feared. Detection work follows the capability tiers now bound into `BRIEF.md` §21; commercial-parity expectations are set in `PAID-TOOLS.md` §6.

**Phase 1 — close the credibility gap (days, all local):**
1. Full carrier + confusable data: generate the Unicode tables from `Cf`/`Zs` categories, the tag block, variation selectors and the Unicode consortium's `confusables.txt`; cross-check against `watermarks-remover`'s tables (MIT). Carrier and homoglyph batteries to 100%.
2. Adapt `avoid-ai-writing`'s ~25-category rule set plus its stylometrics (MIT, attribution retained) as a versioned pack via `registerPatternPack()`, inside Opace's span/hash/limitation envelope. Slop battery must fire on fixture-D-class text with zero new false positives on the human corpus.
3. Add `name`, `organisation` and `citation` protected-span kinds (deterministic: honorific/capitalisation heuristics + `(Author, year)`/`et al.` patterns), and surface the protect gate in the checker instead of the hardcoded `not_run` row.
4. Fix the status semantics: pattern `pass` becomes scoped or `inconclusive`; remove or clearly label the two stub checkboxes until their methods exist — six advertised checks with two permanent stubs is exactly the visual-collapse problem §5 of the brief prohibits.
5. One core change, six rebuilds; refresh gate evidence.

**Phase 2 — first real detection (1–2 weeks):**
6. Integrate `c2pa-js` (official, MIT) as `provenance.c2pa`, and accept image/PDF uploads where relevant so the checkbox can actually run.
7. Wire Fast-DetectGPT (current Llama-3-class scoring models) into the Python local engine as the first real `detector.*` method with measured thresholds — the interim brain while Layer 3 trains (§8.4).
8. Start the Layer-3 classifier pipeline: corpus assembly (open sets + fresh BYOK generations + Opace pre-AI human archive), hard-negative training loop, distil, quantise to ONNX (§8.4). Ship in-browser once it beats the rule tier on the battery at ≤1% measured false-positive rate.
9. Add BYOK adapters for Copyleaks and Originality (the owner already holds accounts) so every surface can show authorised commercial scores alongside the local evidence.
10. One SynthID known-key research fixture (Apache-2.0) in the Readiness Lab, with wrong-key/attack/length behaviour proven.

**Phase 3 — publish and measure (owner-gated):**
10. GitHub repository first (the project is not open source until it exists publicly), then npm/PyPI, WordPress.org, Chrome Web Store — all rebuilt with Phases 1–2 inside.
11. Real-corpus benchmark replacing the synthetic BENCH data; first public Index only after the brief's statistical gates pass.
12. AI-Scribe/AI Hub adapters after their release freeze, per the existing binding boundary.

## 8. Target architecture — one brain, many shells

The owner's requirement: a standard, consistent engine used identically by the website page, WordPress plugin, Astro integration, Chrome extension and CLI; as accurate as achievable and better than the free/open-source field; slick UI on every surface; and no GitHub accounts, terminals or installs for end users.

### 8.1 The brain: one layered signal engine, one package

A single versioned engine (`@opace/content-integrity-core` + `…/browser`, compiled once, bundled into every shell) with five layers. Every layer emits the same evidence envelope (span, hash, severity, limitation, rule/pack version) into the existing contract — the receipts and UI don't change shape as layers are added.

| Layer | Contents | Runs | Source |
|---|---|---|---|
| 0 — Normalisation & carriers | Full Unicode carrier/confusable data, generated from Unicode data files, not handwritten | Everywhere (pure JS, microseconds) | Unicode consortium data + `watermarks-remover` tables (MIT) |
| 1 — Rule packs | Adapted `avoid-ai-writing` categories + an Opace British-English editorial pack; monthly-updatable data, semver'd | Everywhere | `avoid-ai-writing` (MIT, attribution) + Opace |
| 2 — Stylometrics | Burstiness, type-token ratio, function-word trigram entropy, punctuation distribution | Everywhere (pure JS, milliseconds) | Adapted from same + literature |
| 3 — Local model | A small distilled AI-writing classifier via ONNX Runtime Web/WebGPU, lazy-downloaded (~20–50MB) after explicit consent, cached by the browser | Website, extension, WP admin, Astro toolbar — **no install, no account, still local** | Opace-distilled or an openly licensed checkpoint, benchmark-gated |
| 4 — Heavy/optional adapters | Binoculars/Fast-DetectGPT (Python loopback engine), `c2pa-js` provenance, BYOK commercial providers, future official Anthropic verifier | Opt-in; CLI/power users and file inputs | Existing engine + official packages |

Calibrated ensemble on top: layers report independently (the brief rightly bans one fake "human score"), but a versioned combination model — calibrated on the real benchmark corpus, never invented — orders the evidence and drives the UI's "needs review" grouping.

### 8.2 Consistency: kill the parity ports

The current design has three parallel analysis implementations (TypeScript, PHP, Python) that must be kept identical by hand — that is a drift machine, and it triples the cost of every Phase-1/2 upgrade. Instead:

- **The JS engine is the only analysis implementation.** The WordPress plugin already bundles browser-safe JS — make its admin Worker the analysis path and reduce PHP to orchestration, REST, persistence and receipts. The Python service keeps only what genuinely cannot run in JS (Layer-4 models), consumed through the existing job contract.
- **One signal-set version string** (e.g. `signals/2026.09.0`) covering carrier data + packs + stylometrics + model manifest, stamped into every receipt on every surface. Two surfaces on the same version must, by definition, produce byte-identical findings for identical input.
- **The §6 fixture battery as a cross-surface CI gate**: golden fixtures run through web Worker, WP bundle, extension, Astro and CLI on every release; any divergence fails the build. (The existing G1/G2 gates already prove this pattern works — point them at the battery.)

### 8.3 "Better than what's out there", honestly

Beating the free/open-source field is achievable and measurable: adopt their data as the floor (superset coverage), add the layers none of them combine (stylometrics + local model + ensemble calibration), and add what nobody has (protected-fact gates, hash-only receipts, honest per-method states, and the same result on every surface). The battery plus the real-corpus benchmark is the proof mechanism — publish those numbers, per the brief's gates, rather than claims. Matching Pangram-class proprietary detectors is not a promise to make; "the most capable free, local, evidence-led checker" is defensible and is the brief's actual positioning.

### 8.4 Building Layer 3 — the trained classifier (the actual brain)

`PAID-TOOLS.md` proves rules and stylometrics cannot catch well-prompted AI text; only a trained model can. Pangram published its training recipe (arXiv:2402.14873), so the method is not a secret — the moat is data curation, and that is buildable:

1. **Corpus.** Start from open corpora (RAID, HC3, M4, the PERSUADE/Ghostbusters human sets), then add what the open corpora lack: fresh generations from **current** models (GPT-5.x, Claude, Gemini) produced through Opace's own BYOK keys across the domains that matter to us (marketing pages, blogs, product copy, UK business writing), plus verified pre-AI human text (Opace's own client archive is a genuinely rare asset here). Stale corpora are why open detectors decay; a refresh pipeline is the differentiator.
2. **Training loop.** Implement Pangram's published *hard negative mining with synthetic mirrors*: train an initial small classifier; scan a large human pool; every human text it wrongly flags joins the training set together with an LLM-generated "mirror" of the same content; retrain and repeat. This is the single highest-leverage technique for driving the false-positive rate down — which `BRIEF.md` (false-positive honesty) already makes our priority axis.
3. **Model target.** A distilled transformer small enough to quantise to int8 ONNX at roughly 20–50MB — DeBERTa-v3-small/xsmall-class or similar — lazy-loaded, cached, running via ONNX Runtime Web (WASM, WebGPU where available). Sentence-window scoring aggregated to spans, so the UI can highlight like the paid tools do.
4. **Include a hand-rewritten-AI category** in training and evaluation (the owner can supply real examples) — the class where commercial tools diverge most and our Index can say something nobody else measures.
5. **Interim step while the distilled model is being built:** wire Fast-DetectGPT into the Python local engine with a current scoring model — its January 2026 update (Llama-3-8B pairs) reports substantially better results on newer-model text. That gives the CLI/power-user tier a real detector within days, and produces the calibration data the benchmark needs.
6. **Calibration and honesty.** Publish the operating point (threshold, measured FPR/TPR per domain, corpus version) with every release. Scores surface as `attention`/`inconclusive` evidence with the method's measured error rates attached — never as "proof". This is the evidence-led framing the brief demands and no vendor provides.

### 8.5 Will it behave the same on every channel? Yes — by construction, with these rules

The consistency guarantee is architectural, not aspirational:

- **One artefact.** Layers 0–3 compile into the single `@opace/content-integrity-core`/`browser` bundle plus one versioned model file (same ONNX bytes, same tokeniser, same hash everywhere). Website, WP admin, Chrome extension, Astro toolbar and Node CLI all load that identical bundle in a Worker; nothing reimplements analysis per channel (the PHP/Python parity ports are demoted to orchestration only).
- **Determinism.** Rules/stylometrics are exact-deterministic. Model inference is near-deterministic across backends; pin the runtime version, quantise to int8, and define golden fixtures with a score tolerance (±0.5 points) enforced cross-surface in CI. Identical input + identical signal-set version ⇒ identical findings, verified on every release by the §6 battery running through web Worker, WP bundle, extension, Astro and CLI.
- **One version string.** `signals/<year>.<month>.<n>` covers carrier data + packs + stylometrics + model manifest and is stamped into every receipt, so two surfaces can be proven equivalent (or proven stale).

**Channel compliance (checked against store rules):**

| Channel | Constraint | How the brain complies |
|---|---|---|
| WordPress.org | GPL-compatible code only; no obfuscation; no CDN-loaded assets; no phoning home without consent; large binaries in SVN frowned upon | MIT/Apache code (ONNX Runtime Web is MIT) is GPL-compatible; JS bundle ships in the ZIP; the model file is **not** bundled — downloaded once from Opace's origin after an explicit opt-in ("Download the local AI-signals model, ~30MB"), stored in the media/uploads dir; weights under a redistributable licence (weights are data, not code); Tiers A–B work fully without the download, so the plugin passes review as complete without it |
| Chrome Web Store | MV3; no remotely hosted **code**; data files may be fetched; size limits | Runtime + WASM bundled in the extension; model fetched on consent into IndexedDB (data, not code — MV3-compliant); Tiers A–B work offline out of the box |
| Astro/npm/PyPI | none material | Model as an optional npm package or first-run download; CLI flag `--with-model` |
| Opace website | none | Same lazy-load pattern with the consent + size disclosure the checker's privacy copy already uses |
| Python local engine | heavier models allowed | Fast-DetectGPT/Binoculars adapters with explicit resource preflight, per Spec 04's existing seams |

One honest caveat to carry in the copy: the browser model download (~30MB, one-off, cached) is the only place "no install" costs a click. Everything else stays paste-and-run.

### 8.6 "Slick UI, no GitHub, no commands"

Layers 0–3 make every user-facing surface self-contained: paste or click, everything local, model download behind a consent toggle with size shown. GitHub/npm/CLI remain distribution channels for developers and for SEO, not prerequisites. The one UI rule to carry through: a check appears only when its method can actually run — stubs are labelled "coming, not yet run" rather than sitting as live-looking checkboxes.
